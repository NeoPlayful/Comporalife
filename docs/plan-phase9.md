## 一、Phase 9 目标

> **让汇率指标可查、可改、可追溯，并让它折算出的每一个数字都对得上**

Phase 8 把汇率这一侧的**内核**收口了：禁止链式套算、缺失即报错、净资产/分析/报表/现金流全链路折算、手工汇率有分页与就地编辑、增删改写审计、输入校验拒绝溢出与未来日期。

但复盘中暴露出三类问题，都不是「再加一个功能」，而是**已经算出去的数字是错的**，或者**已有承诺没有兑现**：

1. **现金流统计完全没做币种折算**。`computeCashflow` 的参数里根本没有基准币种，它把不同币种的分录金额**直接相加**。一笔 USD 支出和一笔 CNY 支出会被当成同一种货币累加。受影响的下游比想象中多：首页「本月收入/支出/储蓄率」、现金流趋势图、财富目标页的「可投资结余」、财务自由测算的年支出、报表现金流。更糟的是它与项目自己的文档口径矛盾——Phase 3 明确要求预算与流水按交易日汇率折算，分析页做到了，同样是收支统计的现金流却漏了。结果是**分析页和首页显示的同期支出金额对不上**，用户一定会发现。
2. **收益曲线的现金口径漏了账户期初余额**。`buildValueSeries` 只累加 `TransactionEntry`，从没加账户期初余额。经真实服务验证：一个期初 10 万的证券账户，收益曲线全程显示 0（有交易时甚至是负数），而同一页面 `/summary` 显示现金 10 万。两者互相矛盾，且用户的全部历史收益都是错的。
3. **汇率精度与审计的边角缺陷**：价格字段是 `DECIMAL(20,8)`，但四处响应与两处导出统一用金额的 6 位格式化，8 位精度被截断；价格校验允许 `0`（一条 0 价会让市值归零且不进「缺价」清单，是最坏的静默错误）；价格与估值快照的增删改**一条审计都没有**，而账户期初余额变更都有审计。

同时，汇率指标缺少一个**独立入口**：它只嵌在设置页底部，没有分页以外的维护能力，用户无法把它当作「指标」来整体查看与校准。

另有一处已建未用：`portfolio_valuations` 表、`GET/POST/DELETE /portfolios/:id/valuations` 接口、`ValuationSource.computed` 枚举全都存在，但**没有任何计算读取它**，手工快照录入后对结果毫无影响，`computed` 快照从未被写入过。

Phase 9 的五件事：

1. **让汇率指标成为一等公民**。独立「汇率指标」页 `/exchange-rates`：分页、新增、就地修改、删除，与设置页共用同一数据但以指标视角组织。
2. **修正现金流折算口径**。按交易日汇率折算到基准币种，缺失汇率时排除该笔并把该月标记为不完整，同时修正全部五个调用方。
3. **修正收益曲线的现金口径**。历史序列必须包含账户期初余额（按 `openingBalanceDate` 判断是否已生效），与 `/summary` 的口径严格一致。
4. **让估值快照真正生效**。缺价时点用手工快照接管证券市值，响应标注来源，图表明示「这几个点来自快照」。
5. **补齐精度、校验与审计**。价格与汇率按字段位宽序列化；价格拒绝 0；价格与估值快照增删改写审计，补中英词条。

> **关于股票/ETF 行情**：持仓价格维护继续留在组合详情页内，作为投资模块的一部分。本阶段**不**开设全局「标的与价格」管理页——那是行情源接入阶段（独立立项）的配套 UI，与汇率指标无关。

### 核心原则

| 原则 | 说明 |
|------|------|
| **口径必须一致** | 同一份数据在首页、分析页、报表里必须给出对得上的数字。现金流与净资产共用同一套汇率折算规则 |
| **精度的位宽由字段决定** | 汇率 `DECIMAL(20,10)` 输出 10 位，价格 `DECIMAL(20,8)` 输出 8 位，金额 `DECIMAL(20,6)` 输出 6 位。不得用金额格式化函数处理汇率与价格 |
| **缺失不撒谎** | 缺汇率时该笔排除并显式告知；缺价格时收益点标记不完整。不按 1:1、不用成本价、不用未来价格回填 |
| **快照是显式替代** | 手工估值快照只在「该时点缺价格」时作为市值来源，且来源永久标记、UI 明示 |
| **入口先于能力** | 后端已实现而用户无法触达的能力，本阶段必须有可见入口，否则视为未交付 |
| **审计覆盖折算输入** | 汇率、价格、估值快照直接决定折算结果与市值，增删改必须留痕 |
| **旧结果可解释** | 本次修正会让既有的现金流与收益曲线发生变化，这是修正错误而非回归；文档与 UI 需说明变化原因 |

### 阶段依赖说明

- **G3 是核心且风险最高**，它改变首页、分析、目标、财务自由、报表五处的数值。必须先做，因为它决定其他阶段「对齐口径」的基准。
- **G2 与 G3 弱耦合**，但同属「口径修正」，建议相邻交付，便于一次性说明数值变化。
- **G1 完全独立**，只读写既有汇率接口，可与任何阶段并行；建议先做，因为它是本阶段最直接的交付物。

- **G5 独立**，只改序列化、校验、审计与枚举。
- **G6 收尾**，必须在接口冻结后进行。

## 四、数据模型设计

### 4.1 模型总览（不新增表）

Phase 9 **不新增任何表，不新增任何字段**。所有能力落在已有结构上：

```
instruments            标的元数据（symbol / name / assetClass / currency / note）
instrument_prices      价格序列（priceDate 唯一，source = manual）
portfolio_valuations   组合估值快照（valuationDate 唯一，source = manual | computed）
exchange_rates         汇率序列（rateDate 唯一，source = manual）
```

**为什么不需要新表**：价格与估值快照的存储形态已经足够。缺的是「读取时如何使用它们」以及「用户能否维护它们」。新增表只会制造第二套口径。

**为什么不给价格加 `quality` 或 `isEstimated` 字段**：可用性是**相对于某个估值时点**的派生判断，不是价格自身的属性。同一个价格在 `asOf = 其日期` 时可用，在 `asOf = 前一天` 时不可用。把派生状态落库会导致写入时无法确定、且随查询条件变化的字段。

### 4.2 既有枚举处置

```prisma
enum PriceSource {
  manual     // 本阶段唯一实际写入值
  imported   // 预留：批量导入
  provider   // 预留：外部行情源
}

enum RateSource {
  manual     // 唯一实际写入值
}

enum ValuationSource {
  computed   // 系统按需生成，本阶段首次真正写入
  manual     // 用户手工录入
}
```

处置原则：**不删除枚举值**（已发布数据库与备份包中可能存在），只在本阶段明确实际写入范围，并在文档标注 `imported`/`provider` 为预留。

### 4.3 价格可用性定义

这是本阶段唯一需要精确到公式的定义。

设：

- 采样日集合 `D = [d₀, d₁, …, dₙ]`（由 `enumerateDates` 按粒度生成）
- 标的 `i` 的价格序列 `Pᵢ = {(date, price)}`，按日期升序
- 组合持仓 `Hᵢ(d)`：截至 `d` 收盘的持仓数量（由交易重放得出）

则标的 `i` 在采样日 `d` 的**可用价格**：

```
price_i(d) = Pᵢ 中满足 date ≤ d 的最后一条的 price，若不存在则该点不可用
```

单点市值：

```
value_i(d) = Hᵢ(d) > 0 时：Hᵢ(d) × price_i(d)，否则 0
```

采样日 `d` 是否为完整点：

```
complete(d) = ∀ i ∈ 组合持仓且 Hᵢ(d) > 0 ：price_i(d) 存在
```

**关键约束（本次修正的核心）**：

- `complete(d) = false` 时，该点 `index = null`，且不得参与 TWR 分段。
- `complete(d) = false` 时，**不得**改用「组合区间末端最新价」或「区间内任一更晚的价格」回填。既有实现正是这样做的，必须停止。
- 若同一天存在多条价格（同键不允许，由唯一约束保证），不涉及选择问题。

**估值快照介入规则（G4）**：

```
若 price_i(d) 不存在，但存在 valuation_snapshot(d') 满足 d' ≤ d 且为最后一条：
    使用快照的 marketValue 作为该日证券市值（覆盖全部持仓，不逐标的计算）
    该点 complete = true，但必须在响应中标记 valuationSource = 'manual_snapshot' 与其 valuationDate
否则：
    complete(d) = false
```

此处「覆盖全部持仓」是有意为之：手工快照是用户对整体证券市值的陈述，无法拆到单标的。逐标的混用会产生无法解释的加总。

### 4.4 计算复杂度约束

| 场景 | 现有实现 | 本阶段要求 |
|------|---------|-----------|
| 单组合日粒度 90 天 | 逐日 × 逐标的一次 `findMany` | 一次查询取回区间内全部价格，内存按 `(instrumentId, date)` 建索引 |
| 多组合净值趋势 | 逐组合逐日 | 组合数 × 日数 ≤ 既有上限，允许并保持；不再新增按日查询 |
| 价格索引构建 | 无 | 统一走 `latestPrices` 的批量化路径，禁止在循环内单查 |

**禁止事项**：在 `for (date)` 循环体内发起数据库查询。既有 `buildValueSeries` 与 `latestPrices` 已按「一次查区间再内存过滤」实现，本阶段维持该形态并在测试中加断言（查询次数上界）。

### 4.5 迁移策略

**无数据库迁移**。本阶段不改变 schema。

唯一的「数据」影响是：修正后端，既有错误曲线在下次查询时自然变为正确值。不需要回填、不需要脚本。

## 五、关键设计决策

| # | 决策点 | 结论 | 理由 |
|---|--------|------|------|
| 1 | 缺价时点如何处理 | 标记 `complete = false`，不回填 | 用未来价格回填历史是最隐蔽的「撒谎」，且无法被用户察觉 |
| 2 | 是否允许插值 | 不允许 | 价格不是连续函数；线性插值会制造从未存在的成交价 |
| 3 | 是否用成本价兜底 | 不允许 | 成本价与市值是两种口径，混用会让浮亏消失 |
| 4 | 手工快照的定位 | 仅在该时点缺价时作为整体市值替代 | 它是用户对整体市值的陈述，不可拆分到标的 |
| 5 | 快照优先于重算还是相反 | 重算优先；有完整价格时忽略快照 | 重算可解释、可复现；快照是缺价时的补丁 |
| 6 | `computed` 快照是否需要 | 需要，但仅作为性能缓存，不作为结果来源 | 历史序列重复计算成本高；缓存必须可失效 |
| 7 | 缓存失效粒度 | 按 `portfolioId` 全量失效（价格/交易/现金流变动时） | 逐日期精确失效的收益不及复杂度 |
| 8 | 价格精度 | 8 位小数，独立 `priceToString` | 基金净值与部分标的需要 6 位以上，现有 6 位截断会丢精度 |
| 9 | 价格是否允许 0 | 不允许，必须 > 0 | 0 价会让市值归零且不进 `missingPrices`，是最坏的静默错误 |
| 10 | 已发布枚举值是否删除 | 不删 | 备份包中可能存在；删枚举会破坏恢复 |

## 七、G2 — 折算口径修正

### 7.1 报表账户明细的 baseBalance 未折算

`report.service.ts` 的 `buildNetWorth` 里，`baseBalance` 被直接赋成原币余额：

```ts
balance: moneyToString(balance),
baseBalance: moneyToString(balance),   // 原币冒充基准币种
```

而同一份报表的 `totals` 来自已折算的净资产计算。结果是**明细行之和与合计行不相等**，外币账户越多偏差越大；`report.export.ts` 又把这个值直接写进导出文件，错误一并带出。

修正：按账户币种逐条折算到基准币种，汇率日期取报表截止日 `ctx.to`；缺汇率的账户 `baseBalance` 留空（`null`），并计入 `completeness.missingRates`，绝不用原币数字冒充。

### 7.2 汇率滞后检查漏掉资产与负债

`findRateLag` 只遍历 `account` 与 `portfolio` 的币种。外币房产、外币贷款缺汇率时：

- 资产页与负债页会提示「缺少汇率、未计入合计」
- 但数据质量总览是**干净的**，首页卡片也不报

两处口径互相矛盾。首页 `/dashboard/data-quality` 的 `missingRateCurrencies` 同样只遍历账户。

修正：两处都把 `asset` 与 `liability` 的币种纳入检查范围，使「资产页提示」「数据质量总览」「首页卡片」三处一致。

### 7.3 验收

- 外币账户的报表 `baseBalance` 等于 `balance × 汇率`，明细之和等于 `totals.assets`
- 缺汇率的账户 `baseBalance` 为 `null` 且出现在 `completeness.missingRates`
- 外币资产缺汇率时，`/data-quality/rate-lag` 与 `/dashboard/data-quality` 都能报出
- 导出文件中不再出现「原币数字写在基准币种列」

## 八、G3 — 现金流折算

### 8.1 现状与缺陷

`computeCashflow` 的签名里没有基准币种：

```ts
params: { userId: string; timezone: string; from: Date; to: Date }
```

它把每笔交易的账户腿金额直接相加，**不区分币种**。一笔 USD 支出与一笔 CNY 支出会被当作同一货币累加。

与项目自己的口径直接矛盾：Phase 3 文档写明「按交易日汇率折算」，分析页（`query.service.ts`）确实用 `resolveRate` 按交易日折算，但同样是收支统计的现金流没有。

### 8.2 受影响的下游（五处）

| 调用方 | 影响 |
|--------|------|
| `GET /dashboard/overview` | 首页「本月收入 / 支出 / 储蓄率」错误 |
| `GET /dashboard/cashflow` | 现金流趋势图每个月都错 |
| `goals.routes.ts` → `computeInvestableSurplus` | 财富目标的「可投资结余」错误 |
| `financial-independence.service.ts` | 财务自由测算的年支出与所需资产错误 |
| `reports/report.service.ts` → `buildCashflow` | 报表现金流错误 |

### 8.3 修正方案

1. 签名增加 `baseCurrency: string`，五个调用方全部传入 `settings.baseCurrency` / `ctx.baseCurrency`。
2. 逐条账户腿折算：非基准币种用 `resolveRate({ from: entry.currency, to: baseCurrency, asOf: transaction.occurredAt })`，按交易日取值，与 `query.service.ts` 一致。
3. 缺汇率的交易**整笔排除**（不是按 0 计入），把币种对写入该月的 `missingRates`，并把该月 `isComplete` 置为 `false`。
4. `CashflowResult` 增加 `baseCurrency` 与 `missingRates`（全局去重）；`CashflowPoint` 增加 `missingRates`。
5. 首页响应 `basis` 增加 `baseCurrency` 与 `missingRates`，前端在现金流图下方提示缺哪个币种对。

> **转账处理**：转账两侧一正一负、求和恒为零，必须取转出侧绝对值。折算时同样按各自币种折算后再取绝对值，不能先跨币种相加。

### 8.4 验收

- 一笔 1000 CNY 收入 + 一笔 100 USD 收入（汇率 7）→ `totalIncome = 1700`
- 外币缺汇率时该笔被排除、`totalIncome` 只含已知币种、该月 `isComplete = false`、`basis.missingRates` 含该币种对
- 转账不计入收支，且跨币种转账的划转金额按转出侧折算
- 区间内无流水的月份仍标记为不完整（保持既有行为）

## 九、G4 — 估值快照与收益曲线

### 9.1 收益曲线漏了账户期初余额

经真实服务验证：期初 10 万的证券账户，`/portfolios/:id/performance` 返回的所有采样点 `value` 都是 `0`（有交易时甚至是负数），而同一页面的 `/summary` 显示现金 10 万。

根因在 `buildValueSeries`：它只用 `prisma.transactionEntry.aggregate` 累加流水分录，**从未加账户 `openingBalance`**。注释写的是「用初始入金 + 累计外部现金流反推现金」，但实现只做了后半句。

这使全部历史收益与 TWR/XIRR 建立在错误的基数上，是本阶段**第二严重的正确性缺陷**（第一是 G3 的现金流不折算）。

修正：现金 = 期初余额（若 `openingBalanceDate <= 采样日`）+ 截至该日的分录之和，与 `computeBalance` 的口径严格一致。

### 9.2 现状与缺陷

| 事实 | 影响 |
|------|------|
| `GET/POST /portfolios/:id/valuations` 已实现 | 接口可用 |
| 前端 `portfoliosApi` 无 valuations 封装 | 用户无法触达 |
| `ValuationSource.computed` 存在但从未被写入 | 枚举值无意义 |
| 删除价格时清理 `source = 'computed'` 的估值 | 清理永不命中，是空操作 |
| 任何计算都不读 `portfolio_valuations` | 手工快照录入后对结果毫无影响 |

### 9.3 接入设计

**读取顺序**（每个采样点 `d`）：

```
1. 若所有持仓在 d 均有可用价格 → 重算市值（权威）
2. 否则若存在手工快照 v 满足 v.valuationDate ≤ d 且为最后一条 → 用 v.marketValue
3. 否则 → 该点 complete = false
```

**`computed` 快照的定位**：仅缓存「重算结果」，用于避免同一 `(portfolioId, date)` 被多个页面重复重算。写入时机为该点重算成功且完整时。读取时**仍以重算为优先**，缓存仅在其输入未变化时复用——本项目当前不需要该优化，且引入会带来失效复杂度，因此：

> **决策：本阶段不写入 `computed` 快照。** 保留枚举值，删除「删除价格后清理 computed」的空操作，改为在文档中标注预留。

这一决策的理由是：现有数据量（个人组合、日粒度 ≤ 几百点）下重算成本可控，而缓存失效的正确性成本远高于收益。**不做比做错更好**。

**手工快照的前端接入**：

- 组合详情页新增「估值快照」区块（列表 + 新增 + 删除）
- 快照列表展示：估值日期、证券市值、来源（手工）、备注
- 录入时若同日已存在快照 → 需显式确认覆盖（后端已支持 `overwrite`）
- 若同日重算值与手填值差异 > 5%，返回警告 `discrepancy`（对齐 `plan-phase4.md` 的原设计，属可选增强）

### 9.4 响应扩展

`GET /portfolios/:id/performance` 每个点新增：

```jsonc
{
  "date": "2026-03-15",
  "value": "123456.780000",
  "index": null,
  "complete": true,
  "valuationSource": "computed" | "manual_snapshot",
  "snapshotDate": "2026-03-01" | null
}
```

保持向后兼容：新增字段，不改既有字段语义（除 `complete` 的正确性修正）。

### 9.5 验收

- 无价格、有快照 → 该点 `complete = true`，`valuationSource = 'manual_snapshot'`
- 无价格、无快照 → `complete = false`
- 有价格、有快照 → 使用重算值，`valuationSource = 'computed'`
- 快照晚于采样日 → 不参与该点
- 前端快照 CRUD 全链路可用

### 9.6 价格可用性判定

#### 9.6.1 现状与缺陷

`server/src/modules/portfolios/valuation.service.ts` 的 `latestPrices` 按 `instrumentId` 分组取 `priceDate <= asOf` 的最新一条，这在**单次当前估值**场景下是正确的（「最近可用价」是行业惯例），但在**历史序列**场景下是错的：它会让 `2026-01-01` 的估值使用 `2026-10-20` 录入的价格。

#### 9.6.2 修正方案

区分两种语义，用两个函数表达，避免一个函数承担两种含义：

| 函数 | 语义 | 使用者 |
|------|------|--------|
| `latestPrices(asOf)` | 截至 `asOf` 的最近可用价，**允许日期早于 asOf 很多天**（这是正确行为） | 当前持仓表、组合总览、净资产当前值 |
| `pricesAsOf(asOf, staleDays)` | 同上，但**同时返回价格日期**，由调用方判断新鲜度 | 历史序列、收益计算 |

关键点在于：**「允许旧价」本身不是 bug，bug 是历史序列不知道自己在用旧价**。因此修正落点是：

1. `valueHoldings` 返回值中，对每个持仓给出 `priceDate`，并新增 `pricedAsOf` 判断。
2. `buildValueSeries` 每个采样点不再只看 `isComplete`（当前只反映「有无价格」），还要看「价格日期是否晚于采样日」——后者在现有实现中因 `lte` 过滤而不可能发生，**真正的缺陷是 `complete` 只在「该标的完全没有任何 ≤ asOf 的价格」时为 false，而用户只录了一个今天的价格时，历史每一天都能查到这条价格**。

因此必须显式引入**价格新鲜度**，而不能只靠「有没有价格」：

```
complete(d) = ∀ i : Hᵢ(d) > 0 ⟹ 存在 price 满足 priceDate ≤ d
```

当 `d` 早于用户首次录价日期时，条件自然不成立 → `complete = false`。这正是要的效果。**不需要额外的 staleDays 参与历史判定**（staleDays 用于「当前估值是否过期」的提示，不用于历史可用性）。

#### 9.6.3 影响面

| 位置 | 影响 |
|------|------|
| `GET /portfolios/:id/holdings` | 不变（当前估值） |
| `GET /portfolios/:id/summary` | 不变（当前估值） |
| `GET /portfolios/:id/performance` | **变化**：`points[].complete` 与 `index` 可能变为 null，`missingValuations` 可能变长 |
| `/dashboard/net-worth-trend` | **变化**：历史时点证券市值可能为 0，序列会出现台阶 |
| 净资产报表 | 仅当前时点，不变 |
| 数据质量「过期估值」 | 不变（判定当前是否过期） |

> **这是本阶段唯一会改变既有数值的修正**，必须在交付说明中明写。

#### 9.6.4 验收

- 只录一条今日价格、回看过去 30 天 → 30 个点中只有今日 `complete = true`
- 按日录满 30 天 → 全部 `complete = true`
- 中间缺 5 天 → 缺的 5 天 `complete = false`，`missingValuations` 列出这 5 天
- 区间查询的数据库调用次数不随天数线性增长（测试断言上界）

## 十六、交付标准与后续衔接

### 功能交付

1. 汇率指标有独立入口，可查看全部币种对、新增、就地修改与删除，支持分页。
2. 首页、分析页、报表、财富目标、财务自由测算的收支金额统一按交易日汇率折算到基准币种；缺汇率时该笔排除并显式告知，不再把不同币种直接相加。
3. 净资产报表的账户明细按币种折算，明细之和等于合计；导出文件不再把原币数字写在基准币种列。
4. 外币资产与外币负债缺汇率时，数据质量总览与首页卡片都能报出，与资产页提示一致。
5. 收益曲线包含账户期初余额，与组合总览的现金数字一致。
6. 没有价格的历史时点明确标记为不完整，不再用最新价冒充历史价；可用手工估值快照作为显式替代，并在图表上标注来源。
7. 汇率、价格、估值快照的增删改均进入审计日志，且审计视图不含数值。
8. 汇率、价格、金额按各自字段位宽序列化，不再出现精度截断。

### 质量要求

1. 同一份数据在首页、分析页、报表三处必须对得上；折算规则共用同一实现。
2. 缺失汇率不得按 1:1 处理；缺失价格不得插值、不得用成本价或未来价格兜底。
3. 精度按字段位宽：汇率 10 位、价格 8 位、金额 6 位。
4. 价格必须 > 0；汇率整数位不得溢出 `DECIMAL(20,10)`，不得录未来日期。
5. 循环体内不得发起数据库查询。
6. 越权一律 404；管理员不可见余额、流水、持仓、目标、报表与标的持仓价格。**Phase 10 修正**：汇率改为系统参考数据，管理员可在后台维护；标的价格仍不可见。
7. 前八阶段全部测试通过（除本阶段明确修正语义的用例）。

### 已知取舍

| 取舍 | 影响 | 后续处理 |
|------|------|---------|
| 现金流数值会变化 | 多币种用户的历史收支会变大或变小 | 这是修正错误；交付说明中明写变化原因 |
| 收益曲线数值会变化 | 期初余额计入后曲线整体抬升 | 同上 |
| 手工价格无法回填历史 | 用户录入前的历史区间仍是断点 | 引导按日补录；批量导入作为后续小阶段 |
| 不生成 `computed` 快照 | 长区间重复计算 | 数据量小可接受；需要时再引入并设计失效 |
| 快照覆盖整体持仓 | 无法逐标的归因 | 明示「快照来自手工，无法拆分到标的」 |
| 不做股票/ETF 全局管理页 | 持仓价格维护仍在组合详情页 | 与行情源接入一起设计 |
| 不做外部汇率/行情接入 | 汇率仍需手工维护 | 独立阶段评估 |
| 不删除已发布枚举值 | 存在永不写入的枚举值 | 注释标注预留 |

### 与后续阶段的衔接

| 后续阶段 | 建议内容 | 对 Phase 9 的依赖 |
|---------|---------|------------------|
| 外部汇率源同步 | 提供方适配器、频率、同步状态、失败降级 | 复用 `exchange_rates` 与 `RateSource` 扩展点；折算内核无需改动 |
