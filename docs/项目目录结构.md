# Comporalife（复利人生）— 项目目录结构

> 版本：个人开源版（Personal）MVP 架构规划  
> 定位：个人财务管理、银行账单分析、投资组合管理、复利模拟与长期财富规划  
> 原则：当前不实现 SaaS 多租户、家庭协作、商业订阅；保留未来扩展空间。

---

## 仓库概览

```text
Comporalife/
├── server/                       # Fastify 5 + TypeScript 后端 API (:4000)
├── frontend/                     # React 19 + Vite 8 前端 (:5173)
├── nginx/                        # Nginx 反向代理，统一入口 (:3000)
├── docs/                         # 项目文档
├── scripts/                      # 开发、备份、维护脚本
├── docker-compose.yml            # nginx + api + postgres + redis
├── docker-compose.dev.yml        # 可选：开发环境覆盖配置
├── .env.example                  # 环境变量模板（不得存储真实密钥）
├── .gitignore
├── LICENSE                       # 开源许可证（正式发布前确认）
└── README.md                     # 安装、使用、开发与开源说明
```

**版本边界**：本仓库为完整可自部署的个人开源版；未来闭源的 Comporalife Cloud 放在独立私有仓库。当前不创建 `tenants`、`tenant_members`、`households`、`subscriptions` 等商业/家庭表，也不添加空壳租户路由。

### 后端架构约束

- `routes/` 负责认证、请求校验、响应封装；金融业务逻辑放入 `modules/`。
- 真实账务采用 PostgreSQL `DECIMAL` / Prisma Decimal 与 `decimal.js`，不可使用 JavaScript `number` 作为账务金额的权威表示。
- 交易记录应区分 **收入、支出、内部转账、投资买卖、信用卡还款**；内部转账和证券买入不得直接算作消费。
- 使用 `transactions` + `transaction_entries` 记录交易及账户变动，确保跨账户转账可追踪、可核对；必要时以冲正代替直接抹除历史。
- 账单导入流程必须经过 **解析 → 字段映射 → 预览 → 去重 → 用户确认 → 入账**；失败批次可重试，不应重复记账。
- 蒙特卡罗模拟通过 Worker Threads 或 BullMQ 后台执行，避免占用 Fastify 请求事件循环；结果记录参数、随机种子、模型假设与计算版本。
- 所有个人业务数据必须有可验证的用户归属；每个查询、更新、删除均按当前认证用户授权，不能仅靠前端传入的 `user_id`。
- 导入的银行账单为敏感数据：限制文件大小和格式、隔离临时文件、脱敏日志、设置清理周期，并支持导出和删除。

### 前端交互原则

- 采用响应式布局，桌面端侧栏、移动端适配导航；可使用简洁深色主题。
- Dashboard 统一呈现净资产、账户余额、月度结余、投资配置与目标进度。
- 复利模拟与真实投资持仓严格区分：**模拟结果不是已实现收益**。
- 金额展示必须包含币种；多币种合计时显示换算基准和汇率日期。
- 导入银行账单必须展示识别结果和重复项，允许用户确认后才正式入账。

## nginx — 反向代理

```text
nginx/
└── default.conf                  # 统一 :3000 入口，/api 转发至 Fastify
```

生产环境：Nginx 托管构建后的 React 静态资源，将 `/api/*` 转发至后端；HTTPS 可由外部反向代理或部署入口终止。不要直接向公网开放 PostgreSQL 和 Redis。

## Docker Compose — 部署服务

```text
docker-compose.yml
├── nginx                        # Web 静态文件 + API 统一反向代理
├── api                          # Fastify 5 服务
├── postgres                     # PostgreSQL 16 持久化数据库
└── redis                        # Redis 7 缓存、限流、任务队列
```

> MVP 可以先在 API 进程中运行轻量任务；账单量或模拟任务增长后，可从同一 `server/` 代码库增加独立 `worker` 服务，不必引入微服务。

## 服务端口

| 服务 | 端口 | 说明 |
|---|---:|---|
| Nginx | 3000 | 统一 Web/API 入口，对外暴露 |
| Fastify 后端 | 4000 | 内部 API 服务 |
| React/Vite | 5173 | 本地开发服务器 |
| PostgreSQL | 5432 | 内部数据库，不直接公网暴露 |
| Redis | 6379 | 内部缓存/队列，不直接公网暴露 |

| `accounts` | 银行、现金、信用卡、证券账户 | `user_id` |
| `transactions` | 交易主记录、类型、分类、导入来源 | `user_id`, `account_id`（可选） |
| `transaction_entries` | 每笔交易涉及的账户变动 | `transaction_id`, `account_id` |
| `categories` | 默认与自定义收支分类 | `user_id` 可为空（系统预设） |
| `import_batches` | 导入文件批次、状态、统计 | `user_id` |
| `import_rows` | 规范化待确认流水、错误、去重标记 | `import_batch_id` |
| `import_rules` | 商户/摘要识别与分类规则 | `user_id` |
| `budgets` | 按月/分类预算 | `user_id` |
| `budget_items` | 预算内分类额度 | `budget_id`, `user_id` |
| `instruments` | 投资标的（代码、名称、类别、币种） | `user_id` |
| `instrument_prices` | 手工价格历史，同日唯一 | `instrument_id`, `user_id` |
| `portfolios` | 投资组合，与证券账户一对一 | `user_id`, `account_id` |
| `portfolio_trades` | 买卖、股息、利息、费用、税费 | `portfolio_id`, `user_id` |
| `portfolio_cashflows` | 外部入金与出金 | `portfolio_id`, `user_id` |
| `portfolio_valuations` | 手工估值快照（可选） | `portfolio_id`, `user_id` |
| `portfolio_targets` | 目标配置权重 | `portfolio_id`, `user_id` |
| `simulation_scenarios` | 复利与蒙特卡罗参数 | `user_id` |
| `simulation_results` | 计算结果、分位数、模型版本 | `scenario_id` |
| `financial_goals` | 目标金额、期限、进度 | `user_id` |
| `exchange_rates` | 汇率及生效时间 | 币种对、日期 |
| `user_settings` | 基准币种、时区、显示偏好 | `user_id` |

**模型说明**：`instruments` / `instrument_prices` / `portfolios` / `portfolio_trades` / `portfolio_cashflows` / `portfolio_valuations` / `portfolio_targets` 已按实际实现列出。**没有 `portfolio_holdings` 表**：持仓、成本与损益全部由 `portfolio_trades` 重放得出，不存第二套权威数据。投资交易的现金腿写入既有 `transactions` + `transaction_entries`（类型 `investment`），与账本保持单一来源。

## 开源版与未来商业版边界

| 设计项目 | Comporalife Personal（当前） | Comporalife Cloud（未来） |
|---|---|---|
| 源代码 | 开源 | 闭源私有仓库 |
| 数据归属 | `user_id`，用户隔离 | 独立设计租户/家庭数据归属 |
| 用户模式 | 多账号注册、各自管理个人数据 | 多租户、家庭邀请、成员授权 |
| 财务计算 | 完整实现 | 复用或封装开源计算内核 |
| 部署 | Docker Compose 自部署 | 云端托管与运维 |
| 计费 | 无 | 订阅、套餐、配额 |
| 当前是否开发 | 是 | 否 |

**扩展策略**：优先保持计算内核、账单解析器和统计服务为不依赖 HTTP/认证的纯业务模块；当前业务数据按 `user_id` 归属。未来商业版引入租户和家庭共享时，应通过明确的数据迁移、授权模型与适配层实现，而非假设当前 `user_id` 自动等价于 `tenant_id`。开源许可在发布前确认，并考虑未来对外贡献代码的商业复用授权。

### 账户与数据库补充

- 统一 `users` 表的 `role` 使用 `super_admin`、`admin`、`user`；`status` 管理启用/禁用状态。
- `login_sessions` 或等价会话版本/撤销记录用于撤销已签发会话。
- `login_logs`、`security_events`、`admin_audit_logs` 存储安全与管理操作元数据，避免存储银行流水或原始账单。
- `system_settings` 存储允许在线修改的非密钥配置；真实 SMTP/数据库密钥继续由环境变量或秘密管理方案提供。
- 普通业务表仍以 `user_id` 为归属边界；管理员路由不能绕过用户业务 API 的授权规则。
- 不创建租户、家庭成员、商业计费相关表。
