## 一、Phase 10 目标

> **汇率是市场事实，不是个人数据。让它只有一份、由一个入口维护、所有人都对得上**

Phase 1 把汇率按用户隔离，理由写在 `plan-phase1.md`：个人自部署，无外部依赖，用户自己录。这在当时是合理的取舍，但它把一个**客观市场事实**存成了**个人数据**，随着使用暴露出三个问题：

1. **同一个数字要被存 N 份**。USD→CNY 在 2026-10-25 的值对所有人相同，但当前每个持有美元的用户各存一行。`ExchangeRate` 的唯一键是 `(userId, baseCurrency, quoteCurrency, rateDate)`，`resolveRate` 的每条查询都带 `userId`。存量数据越多，重复越严重；同一天同一对出现两个不同的值也不是不可能（两人各自录入的时点不同，或有人录错）。
2. **维护责任错位**。汇率需要持续、准确地更新，这属于运维职责，却被摊到每个用户头上。用户漏录一天就出现「汇率滞后」，漏录一个月就得逐日补。用户既没有行情源，也没有校验手段。
3. **自动同步会被用户维度放大**。如果维持按用户存储，N 个用户就需要 N 次外部调用，或者调一次再按用户去重落库；「手工优先」规则还要在每个用户维度上分别判定。这是把共享数据强行做成了私有数据，然后为它付出 N 倍成本。

Phase 10 的四件事：

1. **汇率全局化**。`ExchangeRate` 去掉 `userId`，唯一键改为 `(baseCurrency, quoteCurrency, rateDate)`。折算内核 `resolveRate` / `convertMany` 去掉用户维度，8 处调用点同步调整。一次抓取、一份存档、所有用户共享同一组数字。
2. **后台汇率管理**。管理后台新增「汇率管理」菜单：列表、分页、按币种对与日期筛选、新增、修改、删除，以及**自动同步未覆盖的币种对提示**（帮助管理员决定该补哪几对）。汇率从「用户财务明细」重新归类为「系统参考数据」，因此管理员可见——这是对第九阶段红线的一次有意收窄（见 5.2）。
3. **用户端只读 + 自选列表**。原来的「手工维护汇率」页改为「汇率指标」：汇率只读，用户像自选股票一样挑要看的币种对；默认跟随自己持有的外币。**用户不能再写汇率**。自选只影响展示，绝不影响折算——折算需要哪些币种由账户、资产、负债的实际币种自动决定。
4. **外部汇率源自动同步**。定义可替换供应商适配器，首期实现通用 JSON 适配器；按「所有用户实际使用的币种并集」一次性抓取并写全局；失败不写任何数据，状态如实暴露；手工（后台录入）优先于自动。

### 核心原则

| 原则 | 说明 |
|------|------|
| **一份事实，一个入口** | 同一币种对同一天全局只有一行；写入入口只有两个：后台人工录入、自动同步 |
| **用户只读，列表自选** | 用户端任何接口都不得写汇率；能改的只有「列表里显示哪几对」，与自选股票同理 |
| **显示与折算解耦** | 用户自选的币种对只影响列表展示；折算币种集合由账户、资产、负债的币种自动推导，不允许用户手工决定，否则会出现「忘了勾选 → 净资产少算」的静默错误 |
| **可添加即可折算** | 候选币种对以真实汇率行为准（直接或反向存在），不是支持的币种全集；加进列表的行不会永远无值 |
| **写库是唯一副作用** | 抓取只发生在定时任务与后台手动刷新；任何读接口只读库，请求路径上不得出现外部调用 |
| **不编造历史** | 只写供应商返回日期（且必须 ≤ 今天）那一行，不回填过去任意日期 |
| **人工优先** | 同币种对同日已有后台人工录入时，自动同步跳过；人工行是权威值 |
| **折算内核不动** | 链式套算仍然禁止。供应商只给锚定币报价时，由同步在**写入阶段**换算成直接对，读取侧永远只见直接对 |
| **缺失不撒谎** | 失败不写占位行，不用上次值、不用 1:1 兜底。状态接口区分「从未同步」「同步失败」「未录入」 |
| **密钥只出不进** | 供应商密钥仅存在于环境变量；任何接口只返回 `configured: true/false`，日志、审计、错误消息均不含密钥 |
| **默认关闭** | 自动同步需管理员开启。不配置任何外部依赖时，系统行为与第九阶段一致 |
| **失败要自限** | 连续失败达阈值自动停用，不无限重试消耗配额；恢复需人工触发 |
| **一次同步一条审计** | 逐行审计会淹没真实操作；同步按「一次运行」记一条，metadata 只含币种对与计数 |

### 阶段依赖说明

- **H1 是硬前置**，其余全部依赖全局数据模型。
- **H2 与 H3 可以并行**：两者只依赖 H1 的表结构，互不依赖对方的接口。
- **H4 与 H2/H3 并行**：适配器只产出 `{pair, rate, date}`，与页面无关。
- **H5 依赖 H1 与 H4**：写全局表 + 消费适配器。
- **H6 收尾**，必须在接口冻结后。

## 三、Phase 10 范围界定

### 交付范围

| 模块 | 交付内容 |
|------|---------|
| 全局汇率表 | `ExchangeRate` 去 `userId`；唯一键 `(base, quote, rateDate)`；单行单值 |
| 折算内核 | `resolveRate` / `convertMany` 去用户维度；8 处调用方调整；查询逻辑（直接 → 反向 → null）完全不变 |
| 后台汇率管理 | `/admin/exchange-rates` 菜单：列表分页、按币种对/日期范围筛选、新增、修改、删除、同步失败补录提示 |
| 用户端自选 | 汇率指标页只读；自选币种对（可增删、可恢复默认）；缺失行保留标记；设置页手工汇率区移除 |
| 供应商适配 | 统一适配器接口；通用 JSON 适配器；密钥仅环境变量；错误码映射与脱敏 |
| 全局自动同步 | 按「全部用户实际使用币种并集」抓取；一次抓取写全局；人工优先跳过 |
| 数值校验 | 拒绝 ≤0、非有限数、整数位溢出；相对上次值偏离超阈值拒绝该对 |
| 调度与锁 | 每日一次，启动延迟；Redis 单飞锁；连续失败自停用 |
| 同步状态 | 每个币种对的来源、最新日期、滞后天数、最近失败原因；运行记录 |
| 审计 | 后台汇率操作记 `admin.currency_rate.*`；同步记 `currency_rate.synced`；均不含数值 |
| 备份兼容 | 备份结构升 v3，汇率移出用户备份域；恢复 v2 包时该域忽略并警告 |
| 导出 | `exchange_rates.csv` 仍在导出中，标注为「系统参考数据快照」 |

### 明确不交付（后续阶段）

| 能力 | 原因 |
|------|------|
| 股票与 ETF 行情自动接入 | 另一套语义（交易日历、复权、停牌、拆股），与汇率共用调度会互相拖累 |
| 历史汇率批量回填 | 回填等于替用户决定当时用哪个汇率，与「不编造历史」冲突 |
| 实时推送 / WebSocket 汇率 | 个人版按日看数字足够；实时化只消耗配额并引入长连接复杂度 |
| 多供应商并行与故障转移 | 需要来源优先级与「这条来自谁」的排序规则，属独立设计 |
| 跨币种转账 | `plan-phase1` 已定禁止，与汇率存储方式无关 |
| 放开链式套算 | 本阶段刻意用写入阶段换算绕开，读取侧规则不变 |
| 用户自带密钥 | 与个人版单租户定位不符，且会把密钥引入备份范围 |
| 用户直接写汇率 | 本阶段的核心决策：写入入口只保留后台与自动同步 |
| 汇率版本历史（同一天保留多个修正版本） | 存档语义定为「每个币种对每天一条」，修正即覆盖；版本历史需独立设计（见 15.3） |

> **口径说明**：本阶段修改《API接口全面分析》第 20 节（三个 `market-data` 接口从预留到实现、汇率接口改为全局、用户侧写接口下线、后台汇率接口新增、新增自选列表接口），并在文档中标明汇率已从「用户数据」改为「系统参考数据」。

## 四、数据模型设计

### 4.1 变更总览

| 变更 | 内容 |
|------|------|
| 字段删除 | `ExchangeRate.userId` 与其索引、外键 |
| 唯一键重设 | `(baseCurrency, quoteCurrency, rateDate)` |
| 枚举扩展 | `RateSource` 增加 `provider`；`manual` 语义改为「后台人工录入」 |
| 新表 | `RateSyncRun`（每次抓取运行一行） |
| 字段新增 | `UserSettings.rateDisplayPairs Json?`（自选汇率列表；null = 跟随默认） |
| 已删除 | `RatePairRequest` 模型与 `PairRequestStatus` 枚举（v10.3） |
| 不改动 | 折算查询逻辑（直接 → 反向 → null）、禁止链式套算、精度位宽 |

### 4.2 `ExchangeRate` 全局化

```prisma
model ExchangeRate {
  id            String     @id @default(uuid()) @db.Uuid
  baseCurrency  String     @map("base_currency")
  quoteCurrency String     @map("quote_currency")
  rate          Decimal    @db.Decimal(20, 10)
  rateDate      DateTime   @map("rate_date") @db.Date
  /// 后台人工录入（权威值）或外部汇率源自动写入
  source        RateSource @default(manual)
  createdAt     DateTime   @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt     DateTime   @updatedAt @map("updated_at") @db.Timestamptz(6)

  @@unique([baseCurrency, quoteCurrency, rateDate])
  @@index([baseCurrency, quoteCurrency, rateDate(sort: Desc)])
  @@index([rateDate(sort: Desc)])
  @@map("exchange_rates")
}
```

```prisma
enum RateSource {
  /// 后台人工录入；自动同步不得覆盖同日同键的人工值
  manual
  /// 外部汇率源自动写入
  provider
}
```

**为什么保留 `manual` 这个名字而不改成 `admin`**：已发布的枚举值与备份包中可能存在该字符串，改名需要数据迁移与恢复兼容处理，收益只是命名更准。改为在注释与文档中明确其语义为「后台人工录入」。第九阶段已确立「不删除已发布枚举值」，这里沿用同一原则。

**为什么保留 `updatedAt`**：单行单值意味着修正即覆盖，需要能看出这一行最后一次被改动的时间，用于排查「某天的汇率是不是被改过」。

### 4.3 存量数据合并策略

全局化后，原本分散在多个用户下的同键行会冲突。迁移必须**确定性**地处理：

```
按 (baseCurrency, quoteCurrency, rateDate) 分组
  ├─ 组内只有 1 行 → 直接保留
  └─ 组内多行 → 保留 createdAt 最早的一行（当时最先被记录的值）
                丢弃其余行，并输出到迁移报告
```

**为什么保留最早的**：汇率是时点事实，最早记录的那一版最接近「当天真实使用值」；后续重复录入更可能是重复劳动或误操作。但这只是默认规则，不是真理——因此迁移必须输出报告，列出：

- 冲突的币种对与日期
- 保留的值与来源用户
- 丢弃的行数与值

**报告必须留存**，供管理员在后台核对。若发现某组应保留另一个值，管理员可直接在后台修改该行。

**当前本地库 `exchange_rates` 为 0 行**（已核实），因此实际迁移不会丢数据。但计划按「有数据」的情形设计，避免只在空库上验证过。

**不保留 `userId` 到任何替代字段**：如果保留「原录入者」列，就变成了半私有数据，用户仍会期待「我的汇率」；写入入口已经收归后台，保留该列没有用途。备份包中的旧行在恢复时会丢弃 `userId` 字段（见 11.1）。

### 4.4 自选汇率列表（`UserSettings.rateDisplayPairs`）

**v10.3 修订：原 `RatePairRequest` 模型已删除。**

最初的方案是让用户「申请新增币种对」，由管理员审核。实施后发现申请机制没有带来实际收益：

- `collectRateDemand` 已经从**全站实际持有的币种**推导抓取范围，不依赖任何申请。
  用户申请 EUR→CNY 时，只要他真有欧元账户，同步本来就会抓这一对。
- 批准本身不写汇率值（凭空造行等于编造数据），所以申请只是「告诉管理员有人想要」，
  属于信息传达，而不是数据维护。
- 代价是：一张表、一套审核接口、一套后台 UI、一组错误码与一组权限判断。

**替代方案：自选列表**，与自选股票同一个模型——数据是系统的，看什么是自己的。

| 维度 | 归属 | 用户能否改 |
|------|------|-----------|
| 汇率值、币种对是否存在 | 系统（后台录入 + 自动同步） | 不能 |
| 列表里显示哪几对 | 个人 | 能 |

存储沿用已有的 `UserSettings.rateDisplayPairs`（`Json?`），语义从「展示黑名单」改为
「自选白名单」，避免新增表与迁移：

- `null` 表示**跟随默认集合**：自己账户/资产/负债的币种 → 基准币种。
- 非 `null` 表示显式列表；增删后自动转为显式列表。
- 空数组是用户的明确选择（清空列表），**不退回默认**。

**可添加范围（关键约束）**：服务端只给出两类候选——

1. 当前**真能折算**的币种对，即 `exchange_rates` 里存在直接或反向汇率行；
2. 用户**确实需要**但暂时没有数据的币种对（自己持有的外币 → 基准币种）。

第一类保证「加进来就有值可看」；第二类保证缺失汇率的需求不会因为没有数据而无法加入。
折算不允许链式套算，所以「EUR 这个币种存在」不等于「EUR→CNY 能算」，候选因此必须
以**真实汇率行**为准，而不是以支持的币种全集为准。

**失效不静默**：管理员删掉某对的数据后，该行保留并显示 `missing`，提示去后台补录；
不会自动从列表里消失——静默消失会让用户以为是自己操作错了。

**上限**：沿用 50 对。列表只是展示偏好，任何折算逻辑都不读它。

**退出同一入口**：`/api/settings` 与 `/api/profile/preferences` 不再接受 `rateDisplayPairs`
写入，否则可以绕过「候选必须可折算」的校验，塞进永远无值的行。读写只走
`/exchange-rates/watchlist*`。

> 已删除：`RatePairRequest` 模型、`PairRequestStatus` 枚举、`rate_pair_requests` 表
> （迁移 `20261025120000_drop_rate_pair_requests`，不可逆）、
> `/exchange-rates/pair-requests*` 与 `/admin/rate-pair-requests*` 接口、
> `RATE_PAIR_REQUEST_EXISTS` 错误码。
>
> 申请删除后管理员如何知道该补哪些币种对：后台汇率管理页新增「自动同步未覆盖的币种对」
> 区块，直接读 `rate_sync_runs.failures`，并支持一键带出补录表单。信息没有丢，只是不再
> 需要用户先提交一次。

### 4.5 `RateSyncRun`

```prisma
model RateSyncRun {
  id             String      @id @default(uuid()) @db.Uuid
  /// 后台手动触发时记录管理员；定时任务为空
  triggeredBy    String?     @map("triggered_by") @db.Uuid
  trigger        SyncTrigger
  provider       String
  anchorCurrency String      @map("anchor_currency")
  status         SyncStatus  @default(running)
  startedAt      DateTime    @default(now()) @map("started_at") @db.Timestamptz(6)
  finishedAt     DateTime?   @map("finished_at") @db.Timestamptz(6)
  /// 供应商返回且通过校验的币种对数量
  fetchedPairs   Int         @default(0) @map("fetched_pairs")
  writtenRows    Int         @default(0) @map("written_rows")
  /// 因同日已有后台人工录入而跳过的行数
  skippedManual  Int         @default(0) @map("skipped_manual")
  /// [{ "pair": "EUR->CNY", "code": "RATE_DEVIATION" }]
  failures       Json?
  errorCode      String?     @map("error_code")
  /// 截断到 200 字符；不得包含密钥或完整响应体
  errorMessage   String?     @map("error_message")

  @@index([startedAt(sort: Desc)])
  @@index([status, startedAt])
  @@map("rate_sync_runs")
}

enum SyncTrigger { scheduled manual }
enum SyncStatus  { running succeeded partial failed skipped }
```

**状态取值**：

- `succeeded`：所需币种对全部写入或已是最新
- `partial`：部分失败，但有数据可用（**不得当作 succeeded**，否则失败会被平均数掩盖）
- `failed`：一条都没写成功，或供应商层失败
- `skipped`：被锁挡住或功能未开启，本次未真正抓取

**与 v10.0 的差别**：因为汇率已全局化，运行记录不再按用户拆分，`userId` 改为 `triggeredBy`（仅记录是谁点的刷新），不再有「系统级行与用户行」的区分。

### 4.6 `UserSettings.rateDisplayPairs`

```prisma
rateDisplayPairs Json? @map("rate_display_pairs")
```

值形如 `["USD->CNY", "EUR->CNY"]`。为 `null` 表示未设置，此时展示全部。

**为什么用 JSON 而不是新表**：这是一份纯展示偏好，没有独立生命周期、没有跨表查询需求、没有并发写冲突场景（一次覆盖全量）。建表会引入一张只存两个字段的表，以及额外的 CRUD 代码。

**它绝不参与折算**。这一点要在接口注释、计划文档、UI 文案三处都写清楚，因为「勾选」看起来很像「启用」。见 5.4。

### 4.7 迁移策略

**一次迁移**，分三步执行（同一次 `migrate deploy` 内的顺序不可交换）：

1. **建新表**：`rate_pair_requests`、`rate_sync_runs` 与两个枚举
2. **数据合并**：按 4.3 的策略去重，收集报告
3. **改结构**：删除 `exchange_rates.user_id` 外键与索引、删除列、建立新唯一键与索引；`UserSettings` 增加 `rateDisplayPairs`

**回滚可行性**：删除 `userId` 与去重都不可逆。因此迁移脚本必须在执行前先输出一份完整导出（`exchange_rates` 全表 JSON），落到迁移目录，并在文档中写明恢复方式。这是本阶段唯一不可逆的迁移，必须显式对待。

## 五、关键设计决策

| # | 决策点 | 结论 | 理由 |
|---|--------|------|------|
| 1 | 汇率是否用户独立 | 全局共享 | 它是客观市场事实；按用户存会产生 N 份重复与不一致 |
| 2 | 用户能否写汇率 | 不能，只读 + 自选列表 | 维护责任归后台；用户无行情源与校验手段 |
| 3 | 写入入口 | 后台人工 + 自动同步，仅此两个 | 两个入口都要留痕，且规则单一（人工优先） |
| 4 | 同日同键人工与自动谁优先 | 人工优先，同步跳过 | 后台录入是权威值；自动值不得覆盖人的显式决定 |
| 5 | 供应商只给锚定币报价 | 写入阶段换算成直接对 | 折算内核保持禁止链式，读取侧只见直接对 |
| 6 | 供应商返回日期与请求日期不同 | 用供应商日期，且必须 ≤ 今天 | 周末与节假日供应商给最近交易日值，用请求日期会伪装成当天汇率 |
| 7 | 是否回填历史 | 不回填 | 回填等于替用户决定当时用哪个汇率 |
| 8 | 抓取失败是否写占位行 | 不写 | 与「缺失不撒谎」冲突 |
| 9 | 抓取时机 | 定时 + 后台手动，读请求只读库 | 否则每页都带外部超时，配额也会被打穿 |
| 10 | 抓取范围 | 全部用户实际使用币种并集 | 全局表意味着一次抓取服务所有人；需求可由账户币种完备推导，无需用户申请参与 |
| 11 | 多实例并发 | Redis `SET NX PX` 单飞 | 已有 Redis，不引入新依赖 |
| 12 | 连续失败处理 | 达阈值自动停用，人工恢复 | 无限重试会持续消耗配额并把问题埋进日志 |
| 13 | 手动刷新是否走任务表 | 同步执行 | 单次数秒，需要立即看到结果 |
| 14 | 密钥位置 | 环境变量 | 与 `JWT_SECRET`、`FILE_ENCRYPTION_KEY` 一致；进库就会进备份 |
| 15 | 偏离阈值 | 相对上次值超阈值拒绝该对（默认 20%） | 唯一能挡住「供应商放大 1000 倍」的机制 |
| 16 | 自选列表是否影响折算 | 不影响，只影响展示 | 否则「忘勾选」会让净资产静默少算 |
| 17 | 折算需要哪些币种 | 由账户/组合/资产/负债币种自动推导 | 分录币种恒等于账户币种（跨币种转账已禁），该集合完备 |
| 18 | 汇率是否进用户备份 | 不进，升至 v3 | 恢复个人备份不得回滚所有人的汇率（见 11.1） |
| 19 | 用户导出是否含汇率 | 含，但标注为参考数据快照 | 导出的价值在于「当时的数字长什么样」，不是「我的汇率」 |
| 20 | 管理员可见汇率 | 可见（后台管理） | 红线收窄：汇率是系统参考数据；价格仍不可见（见 5.2） |
| 21 | 停止使用的旧行是否清理 | 不清理 | 历史行是历史折算的依据 |
| 22 | 越权 | 用户侧自选按 `userId`；后台按 `admin`/`super_admin` | 与既有守卫一致 |
| 23 | 可添加的候选范围 | 有真实汇率行的币种对 + 自己需要的币种对 | 前者保证「加了就有值」，后者保证缺失需求也能被关注；不以支持的币种全集为准 |
| 24 | 是否保留「申请新增币种对」 | 删除 | 自动同步已按实际持有币种推导范围，申请既不加数据也无额外收益，却带来一张表与一套审核 |

### 5.1 为什么不是「共享 + 个人覆盖」

曾考虑保留 `userId` 可空：为空即全局，有值即该用户的私有覆盖。放弃的理由：

- 折算时要先查个人再查全局，两套来源并存会让「这个数字用了哪个汇率」需要两步解释
- 用户仍会觉得「我的汇率」是存在的，与「汇率由后台维护」的产品定位矛盾
- 私有覆盖行会进备份、进导出、进恢复，把刚刚简化的路径重新复杂化

如果未来确实需要「某用户对某币种对有不同的折算口径」，那是一个**独立的产品能力**（例如多实体记账），应单独设计，不能用汇率覆盖来凑。

### 5.2 产品红线的收窄（必须显式记录）

`docs/plan-phase9.md:839` 原文：「越权一律 404；管理员不可见汇率与价格明细。」决策表第 16 条：「管理员能否查看价格：否」。

本阶段将这条红线**收窄**为：

> **管理员不可见任何用户的余额、流水、持仓、目标、报表、导入内容、标的持仓价格。**
> 汇率与标的元数据属于系统参考数据，管理员在后台可见、可维护。

**为什么汇率可以放开而标的价格不能**：汇率是**跨用户相同的公共事实**，看到 USD→CNY 不会泄露任何人的财务状况；标的价格虽然也是公共行情，但「某标的的最新价格」与「谁持有它」在界面上紧邻，放开价格管理页会让管理员顺理成章地接触到持仓上下文。本阶段只放开汇率，标的价格维护仍留在组合详情页，管理员不可见。

这条收窄必须在以下位置同步更新，否则会出现「文档说不行、代码却允许」的矛盾：

- `docs/plan-phase9.md` 的交付标准与决策表加注「Phase 10 修正」
- `docs/API接口全面分析.md` 的后台接口章节
- `server/src/modules/admin/admin.routes.ts` 顶部注释
- 管理员审计页的说明文案

### 5.3 为什么自选允许添加「暂无数据」的币种对

「可添加即可折算」有个例外：自己确实持有的外币，即使当前没有汇率数据，也应能加入列表。

理由是两种缺失要分开看——「系统没维护这一对」和「我不知道自己需要它」。若只允许添加有数据的币种对，
一个刚开了欧元账户、但汇率尚未录入的用户就无从表达「我需要 EUR→CNY」，只能看到空列表。
因此候选包含「自己需要但暂无数据」的币种对，加入后显示 `missing` 并提示去后台补录，
比让它彻底不可见更诚实。

### 5.4 自选列表为什么不能影响折算

「我选了这几对汇率」听起来像是在说「我关心这些」，但产品上必须严格区分：

| 语义 | 由谁决定 | 影响 |
|------|---------|------|
| 折算需要哪些币种对 | 账户、组合、资产、负债的实际币种 | 净资产、现金流、报表的数值 |
| 列表展示哪些币种对 | 用户的自选列表（`rateDisplayPairs`） | 只有视觉效果 |

如果让自选影响折算，用户在某个页面移除 USD 后，净资产会变小，而他不会把两件事联系起来。这类静默错误最难排查，因此在接口层就要保证：折算函数不读 `rateDisplayPairs`。

## 七、H2 — 后台汇率管理

### 7.1 菜单与路由

`AdminLayout` 的 `ADMIN_NAV_KEYS` 新增一项，位置在「审计」之前、「设置」之后（汇率是运维配置类，与设置相邻）：

```
{ to: '/admin/exchange-rates', key: 'exchangeRates', icon: ArrowLeftRight }
```

对应 `App.tsx` 新增 `<Route path="exchange-rates" element={<AdminExchangeRatesPage />} />`。

**为什么单开菜单而不是塞进现有「设置」页**：设置页现在只有两个开关（注册、邮箱验证），是「部署级开关」的容器；汇率是带分页、筛选、批量操作的数据表，二者体量与交互模式完全不同。塞在一起会让设置页变成一个杂项目录。

### 7.2 页面结构

```
标题：汇率管理
  ├─ 工具栏：币种对筛选、日期范围、来源筛选、新增、立即同步
  ├─ 汇率表：币种对 / 汇率 / 生效日期 / 来源 / 更新时间 / 操作
  └─ 分页：总数、每页 20/50/100
  └─ 同步未覆盖区：最近运行摘要、失败币种对（可一键带出补录）、连续失败提示
```

### 7.3 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/admin/exchange-rates` | 分页列表；支持 `base`、`quote`、`from`、`to`、`source` 筛选 |
| POST | `/api/admin/exchange-rates` | 新增或覆盖同日同键；写 `admin.currency_rate.created` / `updated` |
| PATCH | `/api/admin/exchange-rates/:id` | 修改汇率值；写 `admin.currency_rate.updated` |
| DELETE | `/api/admin/exchange-rates/:id` | 删除；写 `admin.currency_rate.deleted` |

**权限**：全部走 `requireAdmin`。删除与批量操作可选叠加 `requireSuperAdmin`——本计划建议删除不额外提权，因为删除后可由同步重新抓取，且超管提权会让日常维护变得不可用。

**校验**：与现有手工录入一致（`> 0`、整数位 ≤ 10、日期 ≤ 今天），复用 `manualRateSchema` 的思路，但改为后台命名。

### 7.4 审计

| action | metadata（白名单内） |
|--------|---------------------|
| `admin.currency_rate.created` | `baseCurrency`、`quoteCurrency`、`rateDate`、`source` |
| `admin.currency_rate.updated` | 同上 + `changedFields` |
| `admin.currency_rate.deleted` | `baseCurrency`、`quoteCurrency`、`rateDate` |

`status`、`reason` 已在白名单中。**不新增能承载汇率数值的键**。

后台审计视图（`listAdminAuditLogs`）默认只查 `admin.*`，因此这四条动作会自然出现在后台审计页；用户个人审计页按 `userId` 查询，管理员自己的操作会出现在他自己的个人审计里——这是既有行为，可接受。

### 7.5 验收

- 后台菜单出现「汇率管理」，非管理员访问 403
- 列表分页、筛选（币种对、日期范围、来源）均生效
- 新增同日同键返回覆盖语义，来源为 `manual`
- 修改后 `updatedAt` 变化，折算结果随之变化
- 删除后折算回到「缺失」，状态接口报 `missing`
- 同步失败币种对展示在「自动同步未覆盖」区，点击可带出补录表单
- 三类审计动作可查，且都不含数值
- 管理员看不到任何余额、流水、持仓

## 八、H3 — 用户端只读与自选

### 8.1 汇率指标页改造

| 区域 | 改造 |
|------|------|
| 标题与说明 | 改为「汇率指标」，说明「汇率由系统统一维护，可像自选股票一样挑选要看的币种对」 |
| 工具栏 | 移除「新增汇率」；改为「添加币种对」+「恢复默认」 |
| 添加面板 | 按基准/计价币种筛选的候选列表；点一下即加入，已加入的不再出现 |
| 表格 | 每对一行：汇率、生效日期、来源、状态（最新/已过期/暂无数据）、移除 |
| 默认集合 | 未自定义时跟随「自己持有的外币 → 基准币种」 |
| 移动端 | 自选行数少，改用卡片列表，避免横向滚动 |
| 分页 | 移除。自选上限 50 对，一屏内可浏览，分页反而打断「自选」的使用感 |

**默认展示什么**：跟随自己持有的外币，而不是全部汇率，也不是空列表。
理由是三个方案里它同时满足「首屏有内容」和「数据量可扩展」：全部汇率会随日积月累
无限膨胀，空列表则让多币种用户进来什么都看不到。

### 8.2 自选交互

```
用户点「添加币种对」
  → 面板列出候选（可折算的 + 自己需要的）
  → 点候选项 → 立即加入并出现在表格中
  → 行内「移除」→ 从列表消失；列表清空也是合法状态
  → 「恢复默认」→ 清回 null，重新跟随持有币种
```

没有申请、没有审核、没有状态流转。重复添加按幂等处理（返回当前列表，不报错）。

## 九、H4 — 供应商适配与校验

### 9.1 适配器契约

适配器只认识币种与日期，不写库、不读设置、不碰 Prisma：

```ts
export interface RateQuote {
  base: string;    // 供应商锚定币
  quote: string;   // 目标币
  rate: Decimal;   // 1 base = rate quote
  date: string;    // yyyy-MM-dd，供应商口径的生效日
}

export interface RateProvider {
  readonly name: string;
  readonly anchorCurrency: string;
  /** asOf 是服务器的今天（UTC 日期）；实现不得返回晚于它的日期 */
  fetch(asOf: string, quotes: string[]): Promise<RateQuote[]>;
}
```

### 9.2 通用 JSON 适配器

| 配置项 | 含义 |
|--------|------|
| `RATE_PROVIDER_URL` | 请求地址模板，支持 `{date}`、`{quotes}`、`{key}`；空表示未启用 |
| `RATE_PROVIDER_ANCHOR` | 供应商报价锚定币，默认 `USD` |
| `RATE_PROVIDER_KEY` | 密钥；**任何接口与日志都不回显** |
| `RATE_PROVIDER_KEY_PARAM` | 密钥参数名；留空表示无需密钥 |
| `RATE_PROVIDER_RATES_PATH` | 响应中汇率表的 JSON 路径，默认 `rates` |
| `RATE_PROVIDER_DATE_PATH` | 响应中日期字段路径；空则用请求日期 |
| `RATE_PROVIDER_TIMEOUT_MS` | 超时，默认 10000 |

**不做的配置**：条件判断、多级回退、单位换算、嵌套重组。需要这些时为该供应商单独写适配器实现，不把配置做成半个脚本语言。

**安全约束**：

- 只允许 `https://`，加载时校验，不满足直接拒绝启动
- 不跟随到非 https 的重定向
- 响应体上限 1 MB，超出按畸形处理
- 密钥注入后不得出现在日志、审计、错误消息、状态接口
- 错误统一映射为原因码：`TIMEOUT`、`AUTH`、`RATE_LIMIT`、`BAD_RESPONSE`、`NETWORK`、`PROVIDER_ERROR`，不拼原文

### 9.3 数值校验（纯函数）

| 检查 | 不通过 |
|------|--------|
| 币种在 `SUPPORTED_CURRENCIES` 内 | 丢弃，`UNSUPPORTED_CURRENCY` |
| 有限数且 > 0 | 丢弃，`RATE_INVALID` |
| 整数位 ≤ 10 | 丢弃，`RATE_OVERFLOW` |
| 按 `RATE_SCALE` 舍入后仍 > 0 | 丢弃，`RATE_INVALID` |
| 日期合法且 ≤ asOf | 丢弃，`DATE_INVALID` |
| 与最近一条已有汇率偏离 ≤ `RATE_MAX_DEVIATION_PCT` | 丢弃，`RATE_DEVIATION` |

偏离护栏是唯一能挡住「供应商放大 1000 倍」的机制；`0` 由「> 0」挡住，但被放大的值只能靠相对比较。

### 9.4 测试方式

`fetch` 依赖注入（默认全局 `fetch`）。固定响应覆盖：正常多币种、超时、429、401、畸形 JSON、缺路径、混入 `0`/负数/超长整数/`null`/非数字、未来日期、偏离超阈值。

**全量测试不得访问外网**，作为验收项。

## 十、H5 — 调度、锁与同步状态

### 10.1 抓取范围（全局化后的关键简化）

```
S = ({所有 active 账户币种} ∪ {所有 active 组合币种} ∪ {所有 active 资产币种} ∪ {所有 active 负债币种})
    \ {各用户自己的基准币种}
  ∪ {已批准的币种对}
```

**一次调用、一次写入、所有用户共享**。这是全局化带来的最大收益：不再需要「抓一次然后按用户分别落库」，也不存在「用户 A 抓到了但用户 B 没抓到」。

由于不同用户的基准币可能不同（有人用 CNY、有人用 USD），`S` 中包含的是「需要被换算成某个基准币的外币」。写入规则是对每个需要的基准币 B 生成 `c→B` 行，见 10.2。

### 10.2 锚定币换算

设供应商锚定币 A，需要 `c→B`，供应商返回 `R(A→x)`：

| 情形 | 写入 |
|------|------|
| `c === A` | `A→B` = `R(A→B)` |
| `B === A` | `c→B` = `1 / R(A→c)` |
| 其他 | `c→B` = `R(A→B) / R(A→c)` |
| `A === B` 且 `c === A` | 无需写入（同币种恒为 1） |

两次除法以 30 位中间精度完成，最后统一 `roundRate` 到 10 位。**先舍入再相除会放大误差**，这是本阶段最容易写错的一处。

若 `R(A→B)` 缺失，本次按 `PARTIAL` 处理，原因记 `ANCHOR_TO_BASE_MISSING`，不写任何派生行。

### 10.3 写入流程

```
1. 计算 S；为空则记 skipped，不打外部接口
2. 抓取一次拿到 S 的报价
3. 校验每条（9.3）
4. 换算为直接对
5. 对每个 (pair, date)：
   a. 已存在 source = manual → skippedManual += 1，跳过
   b. 已存在 source = provider → 更新 rate（同源刷新）
   c. 否则 → 新建，source = 'provider'
6. 写一条 rate_sync_runs
7. 写一条审计 currency_rate.synced
```

**5b 的语义**：同日同键已有 `provider` 行时允许更新，因为那是「同一来源在同一天被重抓」，覆盖的是自己；只有 `manual` 行受保护。

### 10.4 调度与锁

沿用既有 `setInterval` + `unref` + 启动执行模式（`imports/cleanup.ts`、`jobs/retention.ts` 已在用）。

- **启动延迟**：`RATE_SYNC_STARTUP_DELAY_MS`（默认 60 秒），避免开发模式频繁重启时反复打外部接口
- **间隔**：`RATE_SYNC_INTERVAL_MS`（默认 24 小时）
- **总开关**：`UserSettings` 不再承载开关（汇率已全局），改为 `SystemSetting` 键 `rate_sync_enabled`，由后台设置页控制，默认 `false`
- **单飞锁**：`SET rate:sync:lock <runId> NX PX <RATE_SYNC_LOCK_MS>`
  - 拿不到锁 → 记 `skipped`，不算失败
  - 锁超时（默认 5 分钟）必须显著小于调度间隔
  - 后台手动刷新与定时任务共用同一把锁；拿不到返回 409

### 10.5 连续失败自限

取最近 N（默认 3）次运行，若全部 `failed`，自动把 `rate_sync_enabled` 置为 `false`，并在状态接口返回 `disabledReason: 'consecutive_failures'`。

**为什么按运行记录推导而不是加计数字段**：计数字段需要在成功清零、失败递增、停用归零三处都不出错；按记录推导是幂等的。代价是每次调度多一次索引查询。

恢复：管理员在后台重新开启，或手动刷新成功后自动恢复。

### 10.6 状态接口

#### `GET /api/market-data/providers`（管理员）

```jsonc
{
  "configured": true,
  "provider": "generic-json",
  "anchorCurrency": "USD",
  "keyConfigured": true,
  "enabled": false,
  "lastRun": {
    "startedAt": "2026-10-25T02:00:00.000Z",
    "finishedAt": "2026-10-25T02:00:04.120Z",
    "status": "partial",
    "fetchedPairs": 3,
    "writtenRows": 2,
    "skippedManual": 1,
    "failures": [{ "pair": "EUR->CNY", "code": "RATE_DEVIATION" }]
  },
  "disabledReason": null
}
```

#### `GET /api/market-data/status`（用户可用）

```jsonc
{
  "baseCurrency": "CNY",
  "pairs": [
    {
      "from": "USD", "to": "CNY",
      "required": true,
      "latestRateDate": "2026-10-24",
      "daysLag": 1,
      "source": "provider",
      "state": "fresh"
    }
  ],
  "nextRunAt": "2026-10-26T02:00:00.000Z"
}
```

| state | 条件 |
|-------|------|
| `fresh` | 有行且 `daysLag <= RATE_STALE_DAYS` |
| `stale` | 有行但超阈值 |
| `missing` | 完全没有 `≤ today` 的行 |
| `sync_failed` | 该对出现在最近一次运行的 `failures` 里 |

`sync_failed` 与 `missing` 必须分开：前者要管理员看供应商，后者要管理员补录。混在一起给不出正确建议。

**`required` 的含义**：该对是否属于该用户实际需要的币种对（由 8.1 推导）。用户可能看到自己不关心的对（全局表内容），`required: true` 的才影响他的数字。

#### `POST /api/market-data/refresh`（管理员）

- 同步执行，返回与 `lastRun` 同构的摘要
- 未配置 → 400 `RATE_PROVIDER_NOT_CONFIGURED`
- 正在同步 → 409 `RATE_SYNC_IN_PROGRESS`
- 成功后若此前因连续失败被停用，则自动恢复开关
- 写一条审计 `currency_rate.synced`

### 10.7 保留期

`rate_sync_runs` 按 `RATE_SYNC_RUN_RETENTION_DAYS`（默认 90 天）清理，挂在既有 `runDataRetentionCleanup` 中，与备份、导出、通知、审计一起跑。

### 10.8 验收

- 两个进程同时调度 → 只有一个真正抓取，另一个记 `skipped`
- 无任何外币实体时 → 不打外部接口
- 连续 3 次失败 → 自动停用并给出原因
- 手动刷新成功后开关恢复
- 手动刷新拿不到锁 → 409
- 未配置时刷新 → 400，消息不含端点原文
- 状态接口区分四种 state
- 跨用户：两个用户对同一币种对看到完全相同的 `latestRateDate` 与 `source`
- 一次同步一条审计且不含数值

## 十一、H6 — 兼容、测试与文档

### 11.1 备份与恢复

**决定：备份结构升到 v3，`exchange_rates` 移出用户备份域。**

理由：汇率是全局数据。用户 A 恢复三个月前的备份时，如果汇率也回滚，会把**所有人**正在使用的汇率退回三个月前，且用户 B 的净资产会跟着变化。这是不可接受的连带影响。

| 场景 | 处理 |
|------|------|
| 新备份（v3） | 不含 `exchange_rates` 域；`notes` 明写「汇率属于系统参考数据，不随个人备份回滚」 |
| 恢复 v2 旧包 | `exchange_rates` 域被识别为「已迁移为系统数据」，忽略不写入，`warnings` 加 `exchange_rates_moved_to_system` |
| 恢复 v3 包到新代码 | 正常，无缺失域警告 |
| 恢复 v1 包 | 沿用既有缺域警告机制 |

**`BACKUP_SCHEMA_VERSION` 从 `comporalife-backup-v2` 改为 `comporalife-backup-v3`。**

**与 Phase 8 原则的关系**：Phase 8 立下「备份必须完整或明说不完整」。移除汇率域不违反它，因为 `notes` 会如实说明汇率去哪了、为什么不在包里。含糊其辞才违反。

### 11.2 导出

## 十五、交付标准与后续衔接

### 功能交付

1. 汇率成为全局共享数据，同一币种对同一天只有一份，所有用户看到的数字完全相同。
2. 管理后台新增「汇率管理」菜单，可查看、筛选、新增、修改、删除汇率，并在「自动同步未覆盖」区看到需要补录的币种对。
3. 用户端汇率页改为只读 + 自选：像自选股票一样把要关注的币种对加入列表，可增删、可恢复默认，但**无法写入汇率**。
4. 用户的自选列表只影响展示，不影响任何折算结果；默认跟随自己持有的外币。
5. 管理员可开启汇率自动同步；开启后系统按日抓取并写入全局，一次调用服务所有用户。
6. 后台人工录入的汇率永远不被自动同步覆盖；人工行删除后可被自动补上。
7. 供应商只按锚定币报价时，系统在写入阶段换算出直接对，折算内核的「禁止链式套算」保持不变。
8. 抓取失败不写任何数据，状态接口区分「从未同步」「同步失败」「未录入」「已过期」；连续失败自动停用并说明原因。
9. 密钥只存在于环境变量，任何接口、日志、审计、错误消息都不含它。
10. 不配置任何供应商时，系统行为与第九阶段一致（只是写入入口变成了后台）。

### 质量要求

1. 读请求路径上不得出现外部调用。
2. 汇率按 `DECIMAL(20,10)` 位宽处理，中间运算精度高于最终精度。
3. 同步只写供应商返回日期那一行，且日期必须 ≤ 今天。
4. 审计 metadata 不含任何汇率数值。
5. 用户侧写汇率一律 403；后台一律 admin 守卫；管理员不可见用户财务内容。
6. 全量测试不依赖外网。
7. 前九阶段全部测试通过，折算数值断言不变。

### 15.1 已知取舍

| 取舍 | 影响 | 后续处理 |
|------|------|---------|
| 汇率全局化不可逆 | 去掉 `userId`、去重后无法恢复成按用户存储 | 迁移前导出全表并保存报告；文档写明恢复方式 |
| 用户失去自助录汇率 | 管理员未维护的币种对，用户只能等同步或后台补录 | 自选列表让缺失行可见并给出提示；若长期缺口，需评估是否需要「受控的自助补充」 |
| 单行单值，修正即覆盖 | 看不到同一天被改过几次、改成什么 | 审计只记「谁在何时改了哪一对」，不记数值；需要完整版本历史属独立设计 |
| 同日人工与自动只有一行 | 看不到供应商原值与人工修正的对照 | 运行记录给出抓取与跳过计数 |
| 不回填历史 | 开启自动同步前的历史区间仍是断点 | 引导管理员按日补录；批量导入属后续小阶段 |
| 单个供应商 | 供应商下线则自动同步不可用 | 目标是「有依赖时能安全降级」，不是高可用 |
| 每日一次 | 盘中汇率变化不反映 | 个人版按日看净资产足够 |
| 汇率不进用户备份 | 恢复备份后折算结果可能与备份当时不同 | `notes` 明写原因；这是为了避免影响其他用户 |
| 后台可见汇率 | 红线收窄 | 已在 5.2 显式记录并同步四处文档；标的价格仍不可见 |

### 15.3 需要你确认的一点（存档深度）

本计划把「存档」定义为：**每个币种对每天保留一条，修正即覆盖**。这是当前模型天然具备的能力，也是本阶段采用的定义。

如果你的「存档」还要求**同一天保留多个修正版本**（例如供应商上午给 7.10、下午修正为 7.12，两者都要能查到），那么需要额外设计：

- 加版本号或改为只追加 + 视图取最新
- 所有折算查询改为走「取最新版本」
- 后台列表要展示版本历史
- 备份与导出的语义随之改变

这会额外增加约 4-6 天，且会改变 H1 的迁移形态。本计划默认不做；若需要，应在开工前明确，避免 H1 做完再返工。

### 15.5 开工前建议确认

1. **存档深度**：见 15.3，是否需要在同一天保留多个修正版本。
2. **首期供应商**：本计划只实现通用 JSON 适配器，不绑定厂商；若要内置某家专用适配器，需明确其鉴权与日期口径。
3. **偏离阈值 20%**：对多数法币安全，但对高波动货币可能误杀，需按目标用户调整。
4. ~~申请通道是否必要~~：已决定删除（v10.3）。自动同步按实际持有币种推导范围，申请既不扩大抓取面也不写数据；「供应商不支持某币种」的缺口改由后台的同步失败提示覆盖。
